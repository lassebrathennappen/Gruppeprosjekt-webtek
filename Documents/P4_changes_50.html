1. Administrative details

Imaginary client name: Fedon

Website name: OPA!

Contact person: Fedon, owner of OPA!

OPA! is a Greek restaurant in Trondheim with a modern twist. The website presents the restaurant, the menu and the Friday grill event, and lets visitors reserve a table. The website starts at index.html.

2. Changes from the design (P2)

The website follows the design document in most details: the same pages, colours, fonts, navbar, banner, olive-and-lemon divider and footer. Below are the changes we made while coding, and why.

Navbar and footer are made with JavaScript (layout.js instead of nav.js)

In P2 we planned a file called nav.js for the navbar. We ended up with layout.js, which builds both the navbar and the footer. We did this because the footer is repeated on every page too, so it made sense to handle both in the same file. See Modularity for details.

The current page is marked with aria-current

As planned, the current page is underlined in the navbar. Instead of adding a class by hand on every page, layout.js finds the current page and sets aria-current="page" on the matching link. The CSS uses this attribute for the underline. This works automatically on every page, and screen readers also read the link as "current page".

event.html was renamed to events.html

The page is called "Events" in the navbar, so we changed the file name to match.

Opening hours on more pages

In user testing (P3), most testers looked for the opening hours on the About us page, the Contact page or the homepage, and not in the footer. We therefore show the opening hours next to the address on the homepage and the Contact page, and in a new "Visit us" section at the bottom of About us. They are still in the footer as well. The opening hours are written only once, in layout.js, and every page gets them from there.

Clearer special offer (Menu and Events)

In user testing (P3), some testers did not understand that the grill menu was a special offer, and were confused that the same grill menu was on both the Menu and the Events page. We made these changes:

  • On the Menu page, the category is still called "From the Grill", but it now has a short text explaining that these dishes are our Special Grill menu, with 20 % off on Fridays and a link to the Events page.
  • On the Events page, there is a "See the menu" button that jumps down to the menu.
  • The grill menu on the Events page has a visible heading, "Special Grill menu", and a note that the prices are Friday prices with 20 % off, with a link to the regular prices on the Menu page.

Booked times in the reservation flow

In the design, unavailable dates were greyed out. We also grey out times that are already booked. These buttons are disabled and crossed out, so the user cannot choose them. Since the project has no back end, the booked times are example data in reservations.js. This makes the booking flow feel more realistic.

No footer on the reservation page

The reservation page does not have a footer. We removed it so the user can focus on the booking steps, and so the booking boxes have more room on the screen. The navbar is still there, so the user can leave the booking at any time.

Sticky navbar

The navbar stays at the top of the screen when the user scrolls, as planned in P2. Testers in P3 also asked for this, since they otherwise had to scroll back to the top to change page.

Hamburger menu on phones and tablets in portrait mode

This was not in the P2 design. In P3, testers found the navbar links small on phones. On screens up to 900px wide (phones and iPads in portrait mode), the links are therefore hidden behind a hamburger button. The button opens and closes the menu, and turns into an X when the menu is open. It is a real <button> with aria-expanded, so it works with the keyboard and screen readers, and the Escape key closes the menu. On larger screens the normal navbar is shown.

Same hover effect on the Reservations buttons

In P3, testers noticed that the Reservations button looked different on hover in the navbar and on the homepage. The Reservations button in the navbar now also grows a little on hover, like the buttons on the homepage.

Responsive layout

The mockups were made for a 1440px wide screen. We use the same breakpoints on all pages (1100px, 768px and 576px). On smaller screens the split layout with text and image stacks into one column, and images keep their aspect ratio so they are not stretched.

In P3 we found problems on the iPad in portrait mode, so we made these changes for screens up to 900px wide: On the Events page, the images and text are placed under each other, so the images are no longer stretched, and the grill menu uses the full width in two columns instead of one narrow column. In the footer, the logo is smaller and placed above the information, so it is no longer squeezed against the opening hours.

Image file names

The image names in the P2 file list (for example hero-meze.png) were changed to shorter names such as food.jpg and grandma.jpg. The images are the same type of content as in the design.

5. Modularity

Repeated code is only written once:

  • Navbar and footer: Every HTML page only has an empty <header></header> and <footer></footer>. The shared file scripts/layout.js fills them with the navbar and the footer. If we change a link or the opening hours, we only change it in one place.
  • Active page in the navbar: layout.js also finds the current page and marks the right link, so this code is not repeated on each page.
  • Hamburger menu: The hamburger button and its JavaScript are also in layout.js, so it works on every page without extra code in the HTML files.
  • Opening hours: The opening hours are written once in layout.js. The footer and every element with class="opening-hours" get the text from there, so a change only has to be made in one place.
  • One stylesheet: All pages use the same css/style.css. There is no separate stylesheet for each page.
  • JavaScript in external files: All JavaScript is in the scripts folder and is linked with <script src="..." defer>. Code that is only used on one page, like menu.js and reservations.js, is only linked on that page.

Lasse was responsible for implementing the modularity with layout.js. The whole group was responsible for the shared stylesheet.
